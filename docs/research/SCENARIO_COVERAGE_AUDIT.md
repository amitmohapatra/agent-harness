# Scenario coverage audit: Trellis harness + memory service + agent-runs

> Kept as a living reference ([improvement backlog](IMPROVEMENT_BACKLOG.md)). A snapshot of origin/main on 2026-10-30: statuses change as work lands, and the backlog holds the current status of each gap. `h:` paths are relative to this repository's root.

Read-only audit of **origin/main** on 2026-10-30: harness `01bbec9`, memory service `839bf2f`, agent-runs `86fcc87` (contracts read from `agent-contracts` origin/main). Paths are `repo:path:line`, with `h:` = agent-harness, `m:` = agent-memory-service, `r:` = agent-runs, `c:` = agent-contracts. Code was read from a `git archive` of origin/main, not from the local checkouts (harness local `main` is 50 commits behind).

Status: **EXISTS** = on main and working as described. **PARTIAL** = some of it is there, and the gap is named. **MISSING** = not found (the places searched are named). Work already in flight is marked **[in flight]** and is not counted as missing.

Priority is set by the effect on answer accuracy for a user: **P0** = wrong or invented answers in common cases; **P1** = wrong answers in specific cases, or a common feature missing; **P2** = mostly latency, cost or polish.

### Decision flow today (one question arriving)

1. **Admit.** `agent.run`/`start` with user, thread and tenant. A queued run on a busy thread waits (`concurrency_key`).
2. **Tools.** The toolbox lists local + gateway MCP tools (cached), lints them, publishes them to the catalog, and picks Code Mode if there are ≥3 read-only servers or ≥20 tools.
3. **Memory request** (memory on). Wait for the tool index once per tenant. Decide the window form from the history owner. One `/v1/context` call: query = the raw message, budget = 5% of the window, the tool list.
4. **Memory service.** Route the query; retrieve with hybrid dense + BM25, graph and expansion, applying the similarity floor; pack sections; run the coverage check to set `evidence_status`; produce tool hints and the learned plan; add the thread window (fixed 2,000 tokens / 20 messages) and the summary.
5. **Harness picks tools.** If the best hint is ≥0.5, offer only the hinted and named tools; otherwise offer all tools plus `tool_search`. Add the abstain note if the status is INSUFFICIENT/INCOMPLETE and no tool is confidently hinted.
6. **Input.** `[system prompt][memory context as system message][replayed window][user message]`.
7. **Each model call.** Planning and long-task tools if (≥3 calls or a steps cue) and the window is ≥32k → delegate if wide → harness tools (sorted) → govern → stall guard and step limit → budget → clear old results past 50% of the window → read tools → FitWindow (tools → descriptions → results → turns → memory) → [Deep Agents summarization] → model hooks.
8. **Each tool call.** The bridge runs: journal replay → schema check → hooks → governance (run / announce / ask) → execute with timeout and read retries → same-step dedupe → journal + memory tool record. A >80k-char result becomes a stub for OpenAI, Claude and MCP adapters only.
9. **End.** Write the transcript to memory (if memory owns the thread), record the outcome, run the sampled grounding and judges offline. Memory extracts facts from the user's words only.

**Where the gaps sit in this flow:** step 3, the query is not rewritten for follow-ups (A1/M1). Step 4, the window is fixed and drops big turns (in flight). Steps 5–6, there is no "fetch live values now" rule, and old results are replayed undated (C1/C2/M5). Step 6, the context ahead of the history breaks the cross-turn cache (K1). Steps 7–8, plain ReAct cuts large results with no way back, and there is no code path for aggregation (D1/D2/M4). Step 9, there is no answer check against the tool results before returning (E3), and no run record the next turn can explain from (in flight, arm D).
